# 04. 후킹 함정과 성능

[← 문서 목록](README.md)

이 문서의 항목은 전부 **실제로 밟아본 지뢰**입니다. 그래서 오진하는 데 걸린 시간까지 같이 적어둡니다.

## 1. byref 값 타입 인자는 후킹 금지 ★

IL2CPP 메서드 중 **byref 값 타입 파라미터를 가진 것은 Harmony로 후킹하면 프로세스가 즉사합니다.**

```
Fatal error. System.AccessViolationException: Attempted to read or write protected memory.
   at Il2CppInterop.Runtime.IL2CPP.il2cpp_object_get_class(IntPtr)
   at Il2CppInterop.Runtime.Runtime.Il2CppObjectPool.Get[[System.__Canon]](IntPtr)
   at DynamicClass.(il2cpp -> managed) _qCA(IntPtr, IntPtr*, ChartDifficultyFlag, _Jh, Il2CppMethodInfo*)
```

`SongInfoContainer._qCA(ref SongInfo, ChartDifficultyFlag, _Jh)` 에서 발생했습니다.
`SongInfo` 는 `ValueType`(구조체)이라 첫 인자가 byref 값 타입이고, Il2CppInterop 1.5.1이 만드는
il2cpp→managed 트램펄린이 인자 슬롯을 제대로 잡지 못합니다.

### 오진하기 쉬운 이유

**후킹 등록(`harmony.Patch`)은 멀쩡히 성공하고, 해당 메서드가 처음 호출되는 순간 죽습니다.**
로그에는 후킹 완료 메시지가 찍혀 있고 postfix 는 **한 번도 호출되지 않습니다.**
게다가 하필 게임 업데이트 직후에 터져서 "업데이트로 난독화 이름이 밀렸다"고 오진했습니다.

실제로는 그 업데이트에서 덤프 1,828개 중 **1개만** 바뀌었습니다. 백업 → 재덤프 → `diff -rq` 절차가
1분 만에 오진을 뒤집어 줬습니다([README](README.md) 4장).

### 판별법

덤프 스텁의 `NativeMethodInfoPtr_` 이름을 볼 것. **`byref_<타입>` 이 박혀 있고 그 타입이
값 타입(struct/enum)이면 후킹 금지.**

```
NativeMethodInfoPtr__qCA_Public_Void_byref_SongInfo_ChartDifficultyFlag__Jh_0   ← 위험
NativeMethodInfoPtr__QCA_Public_Void_Single_0                                  ← 안전
```

### 값으로 넘기는 큰 구조체도 위험

`LogicalNotePlayer._Ib(string, long, ValueTuple<...>, string, bool)` 는 byref가 아니지만,
아웃바운드 래퍼를 보면 튜플을 **`il2cpp_object_unbox` 한 생 포인터**로 넘깁니다:

```csharp
*(IntPtr*)(ptr + 2 * sizeof(IntPtr)) = IL2CPP.il2cpp_object_unbox(Il2CppObjectBaseToPtrNotNull(튜플));
```

오브젝트 헤더가 없는 포인터라, 인바운드 트램펄린이 이걸 객체로 오해하면 `_qCA` 와 똑같이 죽습니다.
`ReadOnlySpan<T>` / `Span<T>` 도 byref를 품은 ref struct라 같은 함정입니다.

### 안전하게 확인된 후킹 (전부 인게임 검증)

| 메서드 | 시그니처 | 결과 |
|---|---|---|
| `SongSelectScene._co` | `(_Cg)` 참조형 1개 | OK |
| `GameScene._dK` | `(_Cg)` 참조형 1개 | OK |
| `_Dg._KiA` | `(float, double)` 값형 | OK |
| `SongInfoContainer._QCA` | `(float)` 값형 | OK — prefix 의 `ref float __0` 로 **인자 바꾸기도 됨** |
| `GameScene._IK` (1.0.4b, 옛 `_dK`) | `(_Cg)` 참조형 1개 | OK |
| `_IF._NGA` (static) | `(int, _BF)` → `Sound`(8바이트 struct) | OK — prefix 의 `ref Sound __result` + `return false` 로 **반환값 대체도 됨** |
| `Constrained2D._irA` | `(Material, bool)` 참조형 + 값형 | OK — 호출부 432곳이지만 곡 선택에서 초당 17~26회 (2026-09-24) |
| `SongInfoContainer._qCA` | `(ref SongInfo, …)` | **즉사** |

값형 인자와 8바이트 struct 반환은 들어오는 방향(IL2CPP → 모드) 트램펄린에서도 문제없었습니다(2026-09-23).
위험한 건 byref 값형 **인자** 입니다.

### 우회법

1. **같은 시점에 불리면서 시그니처가 단순한 다른 메서드**를 트리거로 삼는다.
   실제로 `_qCA`(곡 정보 주입) 대신 `_QCA(float)`(재생바 갱신)을 트리거로 썼습니다.
2. **UI/상태 폴링**으로 감지한다.
3. 잃어버린 인자값은 **다른 경로로 역산**한다. `_qCA` 의 난이도 인자는
   `LogicalNotePlayer._Ve`(`alamode0.spc`)에서 확장자를 떼어 `SongChartInfo.Id` 와 대조하면 나옵니다.

**그리고 가장 좋은 우회법은 애초에 후킹하지 않는 것입니다.**
이 게임은 프로퍼티 setter가 거의 다 살아 있어서 [런타임 자료구조 직접 수정](02-런타임-차트-주입.md)이
더 짧고 안전합니다.

## 2. 덤프 스텁은 `static` 을 잃어버린다

`SignatureDumper` 산출물(`Decompiled/`, `Decompiled_Full/`)은 프로퍼티에서 **`static` 수식어가 빠지고**
byref 파라미터 표기도 흐릿합니다.

| 실제 | 스텁 표기 |
|---|---|
| `public static LogicalNotePlayer _Qe` | `public LogicalNotePlayer _Qe { get; set; }` |
| `public static double _re` ~ `_ue` (7개) | 인스턴스 프로퍼티처럼 보임 |
| `_qCA(ref SongInfo, …)` | `_qCA(ref SongInfo 1, …)` — 파라미터 이름이 전부 `1` |

**후킹이나 리플렉션 전에는 인터롭 어셈블리를 직접 디컴파일해서 확인할 것:**

```bash
ilspycmd "<게임>/MelonLoader/Il2CppAssemblies/Il2CppGame.dll" \
         -t Il2Cppifapp.Game.LogicalNotePlayer \
         -r "<게임>/MelonLoader/Il2CppAssemblies"
```

`[CallerCount(n)]` 로 게임 내 호출부 개수도 알 수 있습니다. **`CallerCount(0)` 이면 게임이 안 쓰는
죽은 메서드**라 후킹해도 무의미합니다 — `LogicalNotePlayer._Gb()` 와 `_S._hab()` 가 여기 걸렸습니다.

### 리플렉션 스윕 시 주의

런타임에 난독화 필드의 정체를 값으로 파악할 때:

```csharp
var props = typeof(LogicalNotePlayer).GetProperties(
    BindingFlags.Public | BindingFlags.Instance | BindingFlags.Static | BindingFlags.DeclaredOnly);
```

- **`BindingFlags.Static` 을 반드시 포함할 것.** 안 넣으면 판정 윈도우 7개가 통째로 안 보입니다.
  (스텁이 `static` 을 숨기기 때문에 이 실수를 하기 쉽습니다 — 실제로 했습니다)
- **`DeclaredOnly` 로 상속 멤버를 잘라낼 것.** 안 그러면 MonoBehaviour/Object/Il2CppObjectBase 의
  `name` `enabled` `tag` `hideFlags` `Pointer` `WasCollected` `m_CachedPtr` 가 섞여 노이즈가 됩니다.
- 읽을 타입은 `string` / primitive / enum 으로 제한할 것. 리스트·튜플 프로퍼티는 게터가
  박싱·복사를 하므로 비쌉니다.

## 3. Unity `== null` 은 제네릭에서 안 걸린다

파괴된 Unity 오브젝트는 C# 참조가 null이 아니지만 `== null` 연산자 오버로드가 true를 돌려줍니다.
그런데 **연산자 오버로드는 정적으로 해석되므로 제네릭 `T` 안에서는 적용되지 않습니다.**

```csharp
// ✗ 파괴된 오브젝트를 못 걸러낸다 — 참조 비교가 됨
private static T Keep<T>(T current) where T : UnityEngine.Object
{
    if (current != null) return current;
    ...
}

// ○ UnityEngine.Object 로 캐스팅해야 오버로드가 걸린다
if ((UnityEngine.Object)current != null) return current;
```

같은 이유로 **`??` 연산자도 파괴된 오브젝트를 걸러내지 못합니다.**

```csharp
var container = _pending ?? scene.songInfoContainer;              // ✗
var container = _pending != null ? _pending : scene.songInfoContainer;   // ○
```

## 4. struct 는 되써넣어야 한다

`Il2CppStructArray<T>` 나 `List<T>` 의 인덱서는 값 타입에 대해 **복사본**을 돌려줍니다.

```csharp
var note = arr[0];
note._He = 3;
arr[0] = note;    // ← 이걸 빼먹으면 아무 일도 안 일어난다
```

반대로 `_T`, `_hA` 처럼 **클래스**인 것은 참조라 프로퍼티만 고치면 바로 반영됩니다.
대상이 struct인지 class인지 덤프에서 먼저 확인할 것.

## 5. 성능 — 프레임 드랍의 진짜 원인

인게임에서 체감 가능한 프레임 드랍이 있었고, **범인을 두 번 잘못 짚었습니다.**
결국 구간별 프로파일러를 붙여서야 확정됐습니다.

### 측정 방법

```csharp
long t = Stopwatch.GetTimestamp();
모듈.Tick();
Record("모듈명", t);        // 600프레임마다 평균/최대/합계 보고
```

읽는 법: 60fps 한 프레임 = 16.7ms, 120fps = 8.3ms.

### 실측 결과

**1차 (프로브 켜짐)**

```

SceneRefs        60회  평균 3.7506ms  최대  6.9235ms  합계 225.04ms   ← 진짜 범인
Detectors        60회  평균 0.5622ms  최대 29.9538ms  합계  33.73ms
PollChart        20회  평균 1.1593ms  최대 23.1600ms  합계  23.19ms
```

**2차 (프로브 끔)**

```
Injector+Probe   60회  평균 0.0036ms  최대 0.0068ms  합계   0.22ms
SceneRefs        60회  평균 3.7372ms  최대 5.3941ms  합계 224.23ms   ← 그대로 남음
Detectors        60회  평균 0.0068ms  최대 0.0126ms  합계   0.41ms
PollChart        20회  평균 0.0017ms  최대 0.0035ms  합계   0.03ms
```

### 원인 1: `FindObjectOfType` 이 호출당 3.75ms

Unity 6 + IL2CPP에서 `FindObjectOfType` 은 **호출 한 번에 3.75ms** 입니다. 4종을 매 틱 뒤지면
600프레임당 225ms — 모드 비용의 거의 전부였습니다.

해결:

- 씬 조회를 한곳(`SceneRefs`)에 모으고 디텍터 틱마다 1회만 수행
- **이미 찾은 참조는 파괴될 때까지 재사용** (재탐색 안 함)
- 현재 씬에 없는 것만 60프레임(≈0.5초)마다 다시 탐색
- `LogicalNotePlayer` 는 **static 싱글턴 `_Qe`** 가 있으므로 `FindObjectOfType` 자체가 불필요

### 원인 2: 인게임에서 로그 한 줄이 수십 ms

1차 측정 구간(5초)에서 로그를 찍은 건 프로브뿐이었는데, 8줄에 합계 약 300ms가 나왔습니다.
**`MelonLogger.Msg` 한 줄이 플레이 중에는 30ms대** 라는 계산입니다.

곡 선택 화면에서는 73줄이 5ms였기 때문에 **로그 타임스탬프만 보면 싸 보입니다.**
실제로 "초당 2줄이니 로깅은 원인이 아니다"라고 오판했습니다 — **줄 수가 아니라 한 줄의 단가**를
봐야 합니다.

대책:

- 진단용 상시 로깅은 목적을 달성하면 **끌 것** (플래그로 남겨두기)
- 노트 목록처럼 수백~수천 줄을 찍는 덤프는 곡 시작 1회성이라도, 노트 2,000개짜리 상위 난이도에서는
  히칭이 됩니다. 필요하면 파일 출력으로 돌릴 것

### 원인 3: 매 프레임 IL2CPP 문자열 읽기

`LogicalNotePlayer._Ve` 같은 IL2CPP 문자열 프로퍼티는 **읽을 때마다 managed 문자열로 마샬링**됩니다.
매 프레임 폴링하면 프레임마다 할당이 발생합니다. 폴링 주기를 두면 사라집니다.

### 정리

| 하지 말 것 | 대신 |
|---|---|
| 매 프레임 `FindObjectOfType` | 캐시 + 살아있는 참조 재사용 |
| 싱글턴을 `FindObjectOfType` 으로 찾기 | static 프로퍼티 직접 사용 |
| 매 프레임 IL2CPP 문자열 읽기 | 주기 폴링 |
| 플레이 중 상시 로깅 | 목적 달성하면 끄기 |
| 줄 수만 보고 로깅 비용 판단 | 프로파일러로 단가 측정 |

## 6. 인터롭 래퍼가 게임에 없는 함수를 부른다

`UnityEngine.ImageConversion.LoadImage(Texture2D, Il2CppStructArray<byte>, bool)` 를 부르면 이렇게 죽습니다
(2026-09-24):

```
System.MissingMethodException: Method not found:
  '!0 ByRef Il2CppSystem.ReadOnlySpan`1.GetPinnableReference()'.
```

인터롭 래퍼가 배열을 `Il2CppSystem.ReadOnlySpan<byte>` 로 감싼 뒤 `GetPinnableReference()` 로 고정하는데,
**게임 쪽 mscorlib 에서 그 함수가 스트리핑돼 없습니다.** 빌드는 멀쩡히 되고 호출하는 순간 터집니다.

### 우회 — 래퍼가 하던 일을 직접 풀어 쓴다

래퍼 본문을 `ilspycmd` 로 열어 보면 결국 네이티브 `*_Injected` 를 부릅니다. 그걸 직접 부르면 됩니다:

```csharp
private static unsafe bool LoadImage(Texture2D tex, byte[] data, bool markNonReadable)
{
    IntPtr native = UnityEngine.Object.MarshalledUnityObject.MarshalNotNull(tex);
    if (native == IntPtr.Zero) return false;

    fixed (byte* begin = data)   // 관리 byte[] 를 고정해서 그대로 넘긴다
    {
        var span = new ManagedSpanWrapper(begin, data.Length);   // UnityEngine.Bindings
        return ImageConversion.LoadImage_Injected(native, ref span, markNonReadable);
    }
}
```

`ReadOnlySpan` 을 받는 다른 Unity API 도 같은 식으로 터질 수 있습니다. 증상이 `MissingMethodException` +
`Il2CppSystem.ReadOnlySpan` 이면 이 방법부터 볼 것.
