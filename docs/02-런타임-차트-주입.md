# 02. 런타임 차트 주입 ★

[← 문서 목록](README.md)

**커스텀 차트의 핵심 문서.** 2026-09-10 인게임에서 노트 치환과 레인 조작이 **실제로 동작하는 것을
확인**했습니다. 바이너리 인코더도, Harmony 후킹도 필요 없습니다.

## 1. 한 줄 요약

> 게임이 원본 `.spc` 를 평소대로 파싱하게 두고, **파싱 이후에 만들어지는 런타임 자료구조를
> 직접 수정한다.** 그 자료구조는 전부 public 프로퍼티에 setter까지 살아 있다.

## 2. 데이터 흐름 — 어디를 고쳐야 하는가

```
.spc 바이너리
  └─ Il2Cpp_n._S._Gab(ReadOnlySpan<byte>, string)      ← 파서. 후킹하면 크래시
       └─ ValueTuple<_t, List<_fA>, List<_eA>>          ← 논리 차트
            └─ LogicalNotePlayer._Ib(..., 튜플, ...)     ← 로더. 후킹하면 크래시
                 ├─ LogicalNotePlayer._Ue = 튜플         ← ✗ 여기 고쳐도 아무 효과 없음
                 └─ LogicalNotePlayer._ve (타입 _T)      ← ★ 게임이 실제로 읽는 곳
                      ├─ _vC : Dictionary<_CA, _hA>      ← ★★ 노트 저장소 (side별)
                      ├─ _ZC : Memory<_IA>               (시간 범위)
                      ├─ _ad : Memory<_jA>               (Vector2 좌표 쌍)
                      ├─ _zC : Memory<_eA>               (이벤트)
                      ├─ _Ad/_bd/_Bd : Memory<double>
                      ├─ _cd/_dd : Memory<_cH>, _Cd : Il2CppStructArray<_cH>
                      └─ _XC : Dictionary<long, Memory<_cH>>   (노트 id → 판정 윈도우)
```

### 결정적 실험 — `_Ue` 는 아무 효과가 없다

`LogicalNotePlayer._Ue.Item2`(논리 노트 `List<_fA>`)를 제자리에서 132개 → 1개로 줄이는 데
**성공했지만 인게임에는 아무 변화가 없었습니다.** 로그상으로는 완벽했습니다:

```
[ChartInjector] 'alamode0.spc' 노트 치환: 132개 → 1개
차트 노트 목록 (차트: 'alamode0.spc' / 총 1개 노트)
```

원인은 `_Ib` 가 로드 시점에 논리 노트를 **다른 자료구조로 변환해 두고 그쪽만 읽기** 때문입니다.
`_Ue` 는 사실상 원본 보관용입니다.

이걸 알아채는 데 도움이 된 단서: `Track._gBA` 가 `ReadOnlySpan<_IA>` / `Memory<_cH>` /
`ReadOnlySpan<_jA>` 를 받는데, 이들이 **`_fA` 와 다른 타입**이라는 점이었습니다.

## 3. `_T` — 변환된 런타임 상태 (`LogicalNotePlayer._ve`)

`_T` 는 **클래스**(참조형)라 프로퍼티를 고치면 그대로 게임에 반영됩니다.

`alamode0`(논리 노트 132개) 진입 직후 실측:

| 프로퍼티 | 타입 | 실측값 | 비고 |
|---|---|---:|---|
| `_vC` | `Dictionary<_CA, _hA>` | side 5종 | **★ 실제 노트 저장소** |
| `_ZC` | `Memory<_IA>` | 4096 | `_IA` = double 2개(시간 범위) |
| `_ad` | `Memory<_jA>` | 4096 | `_jA` = Vector2 2개(좌표) |
| `_zC` | `Memory<_eA>` | 1024 | 이벤트 |
| `_Ad` `_bd` `_Bd` | `Memory<double>` | 8096 각각 | |
| `_cd` `_dd` | `Memory<_cH>` | 32384 각각 | 판정 윈도우 풀 |
| `_XC` | `Dictionary<long, Memory<_cH>>` | — | 노트 id → 판정 윈도우 |
| `_YC` `_Dd` `_ed` `_Ed` | `int` | 0 / 330 / 8096 / 2 | |
| `_xC` | `bool` | True | |

**전부 고정 용량 풀입니다.** 4096 / 8096 / 32384 같은 값은 노트 수와 무관하며 132개짜리 차트든
2000개짜리 차트든 같습니다. 즉 **버퍼 길이로 노트 수를 알 수 없습니다.**

## 4. `_hA` — side별 노트 저장소 (여기를 고친다)

```csharp
public class _hA {                                    // ← 클래스. 참조로 직접 수정 가능
    public Il2CppStructArray<_fA> _ye { get; set; }   // 백킹 배열 (실측 4096)
    public Memory<_fA>            _Ye { get; set; }   // 실제로 쓰는 구간
    public int                    _ze { get; set; }   // 개수
}
```

`_T._vC` 의 키는 `_CA` 열거형이고 **5종 전부 존재**합니다:

```csharp
public enum _CA { _QD = 0, _rD = 1, _RD = 2, _sD = 3, _SD = 4 }
```

`alamode0` 의 첫 노트(Bottom Tap)는 `_rD` 컨테이너에 있었습니다. 다섯 개 전부 `_ye` 용량이 4096입니다.

### 노트 개수 줄이기 (동작 확인됨)

```csharp
var np = LogicalNotePlayer._Qe;          // static 싱글턴
var state = np._ve;                      // _T, 클래스

foreach (_CA side in Enum.GetValues(typeof(_CA)))
{
    if (!state._vC.ContainsKey(side)) continue;
    var container = state._vC[side];
    if (container == null) continue;

    int keep = (side == 첫노트의_side) ? 1 : 0;
    container._Ye = container._Ye.Slice(0, keep);
    container._ze = keep;
}
```

결과: 첫 노트 하나만 떨어지고 나머지는 전부 사라집니다.

> **미확정 1.** 위 코드는 `_Ye`(구간)와 `_ze`(개수)를 **둘 다** 설정합니다. 게임이 어느 쪽을
> 읽는지는 분리 실험을 하지 않아 확정하지 못했습니다.
>
> **미확정 2.** 원래 `_ze` 값을 기록하기 전에 덮어써서 **side별 원본 노트 개수를 남기지 못했습니다.**
> 다음 측정 때는 덮어쓰기 전에 찍을 것.

## 5. `_fA` — 노트 구조체와 렌더링/판정 분리 ★★

이 문서에서 가장 중요한 발견입니다.

`_fA` 는 필드가 **18개**인데 public 생성자는 **10개만** 채웁니다. 나머지 8개는 로드 시점에
게임이 계산해 넣습니다. **그리고 렌더링과 판정이 서로 다른 필드를 읽습니다.**

```csharp
// 생성자가 채우는 10개 — 차트 파일에서 온 값
public _fA(long id, long groupId, _CA side, _HA type,
           int judgementTimestampStart, int judgementTimestampEnd,
           _BA startX, _BA endX, _BA startWidth, _BA endWidth);
```

생성자 파라미터 이름이 난독화를 피했습니다 — 필드 의미가 추정이 아니라 **확정**입니다.

| 필드 | 타입 | 생성자 인자 | 실측값 (`alamode0` 첫 노트) | 읽는 쪽 |
|---|---|---|---|---|
| `_ZD` | long | id | 0 | |
| `_ae` | long | groupId | 0 | |
| `_Ae` | `_CA` | side | `_rD` | `_vC` 키 결정 |
| `_be` | `_HA` | type | `_aE` (Tap) | |
| `_Be` | int | judgementTimestampStart | 3429 | |
| `_ce` | int | judgementTimestampEnd | 3429 (단노트라 동일) | |
| `_Ce` | `_BA` | startX | `1/4 (0.25)` | **렌더링** |
| `_de` | `_BA` | endX | `1/4 (0.25)` | **렌더링** |
| `_De` | `_BA` | startWidth | `1/4 (0.25)` | |
| `_ee` | `_BA` | endWidth | `1/4 (0.25)` | |
| `_Ee` | double | *(계산)* | 6429 | `_Be + 3000` — 용도 미확정 |
| `_fe` | double | *(계산)* | -1800000 | 센티넬(미설정) |
| `_Fe` | double | *(계산)* | -1800000 | 센티넬(미설정) |
| `_ge` | long | *(계산)* | -1 | 센티넬(미설정) |
| `_Ge` | bool | *(계산)* | False | |
| `_he` | `_FA` | *(계산)* | `_Ie` | |
| `_He` | int | *(계산)* | **1** | **★ 판정 레인** |
| `_ie` | int | *(계산)* | **1** | **★ 판정 레인** |

### 좌표 타입 `_BA`

```csharp
public struct _BA {
    public readonly int   _KD;   // 분자 (num)
    public readonly int   _lD;   // 분모 (denom)
    public readonly float _LD;   // 계산된 실수값
    public _BA(int num, int denom);   // ← 필드가 readonly 라 반드시 생성자로 만들 것
}
```

하단 노트는 분모 4에 분자 1~5를 씁니다(`1/4`, `2/4`, `3/4`, `5/4`). 저작 포맷의 lane 0~5와
대응됩니다. 스카이 노트는 분모 12/16/24/32 계열입니다.

### 렌더링과 판정이 갈린다는 증거

`_Ce`/`_de` 만 `1/4` → `3/4` 로 바꿨더니:

- **노트는 새 위치로 옮겨져 그려졌습니다** (렌더링 반영 O)
- **판정은 원래 자리에 남아서 새 위치를 쳐도 안 맞았습니다** (판정 반영 X)

그래서 "원본 분자 값(1)과 같은 계산 필드"를 이름이 아니라 **값으로 검색**했더니 `_He` 와 `_ie` 가
걸렸고, 둘을 3으로 바꾸자 **판정이 따라왔습니다.**

```
[변경 전] 계산 필드: _Ee=6429 _fe=-1800000 _Fe=-1800000 _ge=-1 _Ge=False _he=_Ie _He=1 _ie=1
          └ _He 가 원본 분자(1)와 일치 → 3 로 변경
          └ _ie 가 원본 분자(1)와 일치 → 3 로 변경
[변경 후] 계산 필드: _Ee=6429 _fe=-1800000 _Fe=-1800000 _ge=-1 _Ge=False _he=_Ie _He=3 _ie=3
```

> **미확정 3.** `_He` 와 `_ie` 를 **동시에** 바꿨기 때문에 어느 쪽이 진짜 판정 레인인지,
> 혹은 둘 다 필요한지는 아직 모릅니다. 하나씩 끄고 켜면 갈립니다.
>
> 다만 `_ad`(Vector2 좌표 버퍼)는 **건드리지 않았는데도 판정이 따라왔으므로**,
> 적어도 하단 노트 판정에는 `_ad` 가 관여하지 않습니다.

### 레인 바꾸기 (동작 확인됨)

`_fA` 는 **struct** 이므로 인덱서가 복사본을 줍니다. 고친 뒤 **반드시 되써넣어야** 합니다.

```csharp
var arr = container._ye;        // Il2CppStructArray<_fA> — 인덱서로 읽고 쓰기 가능
var note = arr[0];              // ← 복사본

int denom = note._Ce._lD;
note._Ce = new _BA(newLane, denom);   // 렌더링
note._de = new _BA(newLane, denom);
note._He = newLane;                   // 판정
note._ie = newLane;

arr[0] = note;                  // ← 이걸 빼먹으면 아무 일도 안 일어난다
```

## 6. 커스텀 차트로 가는 길

여기까지로 **차트를 런타임에 임의로 바꿀 수 있다는 것**이 증명됐습니다. 남은 작업:

1. **노트 추가.** 지금까지는 지우고 옮기기만 했습니다. `_ye` 백킹 배열이 4096칸이므로 그 안에서는
   인덱스를 채우고 `_Ye`/`_ze` 를 늘리면 될 것으로 보이나 **미검증**입니다.
   `_fA` 를 새로 만들 때는 계산 필드 8개(특히 `_He`/`_ie`)를 **직접 채워야** 합니다 —
   생성자는 안 채웁니다.
2. **파생 버퍼 동기화.** `_ZC`(시간 범위), `_ad`(좌표), `_XC`(노트 id → 판정 윈도우)가
   원본 노트 기준으로 남아 있습니다. 노트를 추가하면 이쪽도 맞춰야 할 가능성이 높습니다.
3. **종료 시각.** `LogicalNotePlayer._xe`/`_Xe`/`_a`/`_A` 는 **마지막 노트의 `judgeEnd`** 와
   같습니다([03번 문서](03-판정-오디오-세이브.md)). 차트 길이를 바꾸면 같이 갱신해야
   재생바와 종료 판정이 맞습니다.
4. **텍스트 → `_fA` 변환기.** [01번 문서](01-차트-포맷과-에셋.md)의 저작 포맷을 그대로 읽어
   노트를 만드는 컨버터. 좌표계(`num/denom`)가 저작 포맷과 동일하므로 변환이 단순합니다.

## 7. 주입 시점

`_ve._vC` 는 **로드가 끝난 뒤**의 자료구조라 타이밍이 빡빡하지 않습니다.
`LogicalNotePlayer._Qe._Ve`(차트 파일명)가 채워지고 `_ve` 가 null이 아니면 준비된 것이고,
첫 노트가 떨어지기 전에만 손대면 됩니다. 실측상 10프레임 주기 폴링으로 충분했습니다.

초기에는 "가장 이른 프레임"을 잡으려고 매 프레임 폴링했는데, `_Ve` 는 IL2CPP 문자열이라
**읽을 때마다 마샬링이 일어납니다.** 불필요한 비용이니 주기를 두는 편이 낫습니다
([04번 문서](04-후킹-함정과-성능.md)).

## 8. 시도했지만 막힌 경로 (기록용)

| 경로 | 결과 |
|---|---|
| `_Ue.Item2` 리스트 수정 | 수정은 성공, **인게임 무반응** |
| `_S._Gab` 파서 후킹 | `ReadOnlySpan<byte>` 인자 — 크래시 예상 |
| `LogicalNotePlayer._Ib` 후킹 | 튜플을 `il2cpp_object_unbox` 한 생 포인터로 받음 — **크래시 예상** |
| `LogicalNotePlayer._Gb()` 후킹 | 인자 없어 안전하지만 **`CallerCount(0)`** — 게임이 안 씀 |
| `_S._hab()` | **`CallerCount(0)`** — 죽은 코드 |
| `_T._ad`(Vector2 좌표) 수정 | 불필요했음 — 판정은 `_He`/`_ie` 를 봄 |

**교훈: 이 게임에서는 후킹보다 "살아있는 자료구조 직접 수정"이 거의 항상 더 안전하고 짧습니다.**
난독화는 이름만 가릴 뿐 프로퍼티 setter는 그대로 살아 있습니다.
